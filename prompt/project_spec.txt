
PROJECT SPEC

Build an interactive network simulator and network-lab sandbox.

Current stack:
- React frontend
- Flask backend
- single page app behavior

Core implemented features:
- drag devices onto canvas
- assign IP addresses
- create links between devices
- support directional links (bi-directional, forward-only, reverse-only)
- simulate `ping` command
- show packet log similar to Wireshark
- Linux-style terminal workflow
- capture controls with `tcpdump` / `capture start|stop|show|clear|status`
- explicit separation between command execution and packet visibility

Implemented device categories:
- Core devices: PC, Server, Router, Switch
- Bluetooth devices: Phone, Laptop, Beacon, Sensor, Gateway
- IoT devices: bulb, lock, tag, camera, thermostat, plug
- Other peripherals: USB storage, keyboard, mouse, webcam, audio, printer

Device capability policy:
- IP-capable types (can send/receive IP traffic, be pinged, have IPs assigned):
	PC, Server, Router, Switch, Gateway, Laptop, Phone, IoT devices with network stack
- Non-IP peripheral types (no IP stack, no MAC, not pingable, IP field hidden in UI):
	usb-storage, usb-keyboard, usb-mouse, usb-webcam, usb-audio, usb-printer,
	beacon, sensor, iot-tag
- Forwarding types (can act as transit hops in BFS path routing):
	switch, router, gateway
- Design rationale:
	A USB mouse on PC-1 is a physical USB attachment, not a network endpoint.
	PC-2 cannot address it at all — there is no route, no IP, no MAC.
	The canvas edge from PC-1 to Mouse-1 represents physical USB attachment only,
	not a routable network path. Commands like lsusb are local to the host they
	are run from and only show devices physically connected to that host via
	canvas edges.
- Traffic counters are hidden entirely on non-IP peripheral device nodes
	(no DEV or IP rows rendered — peripherals generate no network traffic).

Implemented terminal/network behaviors:
- `ping`, `ip addr`, `ip route`, `ip neigh`, `arp -a`
- `lsusb`, `lsblk`, `dmesg` — scoped to SSH host; only shows devices with a
	canvas edge to the current SSH session host. Requires active SSH session.
	Running without SSH context returns an error: "ssh into a device first".
- `bluetoothctl devices|scan|pair|connect|info`
- `ssh <device|ip>` host context sessions
- `ssh <target> via <gateway>` proxied session flow for learning
- `sendpkt <dst> [proto]` synthetic traffic generation from active host context
- Bluetooth-native monitoring mode:
	- `ble connect <device|mac>`
	- `ble status|monitor`
	- `ble read <characteristic>`
	- `ble write <characteristic> <value>`
	- `ble disconnect`
- `man <command>` help pages
- terminal copy/paste support

Implemented traffic and visualization features:
- per-device inbound/outbound traffic counters split into two rows:
	DEV row: all traffic (layer 2 and above)
	IP row: IP-layer traffic only (ICMP, ARP, TCP, UDP, IP, IPv6)
- traffic counter rows hidden entirely on non-IP peripheral devices
- per-link directional traffic counters
- separate inbound/outbound rendered link paths
- packet capture buffering and explicit reveal to packet panel
- Bluetooth packet simulation
- simulated ARP / ICMP / BLE traffic generation
- animated packet movement on links using a visible moving marker (dot/"o")
- request/response directional motion on ping (source->target then target->source)
- source-aware ping execution tied to active terminal session/proxy context

Implemented link realism controls:
- packet loss percentage
- latency
- jitter
- blocked links
- queue capacity
- bandwidth throttling in packets/sec
- RED-style early drop behavior
- visual drop telemetry for blocked, queue, and RED conditions
- presets for Stable / Congested / Hostile links
- simplified link editor with optional advanced controls
- link condition label rendered on each edge showing:
	CAT · loss% · latency±jitter · bwXpps · qX for outbound and inbound directions

Canvas behavior:
- No positional boundaries — devices can be freely placed and dragged anywhere
	in world space (unbounded). Pan to navigate.
- Zoom anchors to mouse cursor position (Ctrl+Scroll)
- Pan via Space+Drag (camera model — inner world layer transforms, viewport fixed)

Data transfer visual challenge (high-level):
- Goal: make learners clearly see data moving between devices during commands such as `ping`.
- Issue encountered: initial animation was difficult to perceive or appeared directionally wrong in some scenarios.
- Root causes addressed:
	- flight duration was too short for easy human perception,
	- source/target selection could produce non-obvious routes,
	- reverse-direction packet rendering needed explicit path-direction correction.
- High-level solution:
	- slowed and lengthened packet flight visibility,
	- made packet marker higher contrast and easier to track,
	- corrected directional travel logic so response packets animate back to source,
	- aligned terminal command source context with simulated packet origin.

Near-term future features:
- richer SSH live-monitoring simulation on IP-capable hosts
- host-level observability commands (`top`, `ss`, `netstat`, log tailing, service status)
- gateway-centric workflows for mixed IP/Bluetooth environments
- per-host role profiles (workstation, server, gateway, attacker)
- scenario scripts for blue-team/red-team training exercises

Longer-term direction:
- richer threat-model scenarios
- protocol-aware filtering / ACL behavior
- service simulation on hosts
- alerting / detection workflows
- training-lab style monitoring and incident response exercises
